# lane 证据落 /tmp 随重启蒸发,子代理落盘声明不实

**日期**: 2026-09-30
**影响**: issue #53 程序 PR1~PR3 的十条 lane 证据日志与 trunk 对照 worktree 在宿主机夜间重启后全部丢失,只能靠会话记录恢复结论;PR4 lane 执行者跑 1h28m 后死于上游 502,其「已落盘」声明与实际不符
**发现人**: 操作者重启后协调者盘点

## 问题

lane 审计的证据文件统一落在 `/tmp/issue53-lanes/`,宿主机一次重启清空全部;执行代理中途死于网络错误后,转写里声称补建重跑过的证据目录实际不存在

## 现象

```sh
ls /tmp/issue53-lanes/
# 无输出,目录整体消失(前一日曾核验过 13 份 pr3 证据)
```

## 根因

错误假设:/tmp 与普通工作目录一样持久。实际 macOS 重启即清。叠加验证流程缺失:子代理的「已落盘」只在它自己的转写里,协调者没有在交付当下立即 `ls` 核验,事后无从补证

## 修复

PR4 证据由接续执行者从零重建(VM 夹具 + docker 交叉产物 + 十条 lane 重跑);结论性内容(坑清单、PR 终态)同步固化到 `~/tmp/`(持久)的交接文档

## 预防

- 审计物落 `~/tmp/` 或仓库内 `.gitignore` 目录,不落系统 `/tmp`;要落 /tmp 就在交付当下即时审计结案
- 子代理声明「已落盘」后,协调者立即 `ls` 核验,这是勾箱的唯一依据,转写不算数
- 长时子代理任务要能断点续跑(产物落持久位置),上游 502 重试耗尽死掉后才有得救
- 证据落盘前若做过掩码,落盘后必须跑泄漏扫描,正则对 `json.dumps` 带空格的形态会失配,不能只信替换成功
